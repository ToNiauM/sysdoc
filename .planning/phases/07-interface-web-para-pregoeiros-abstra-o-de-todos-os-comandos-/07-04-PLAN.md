Criar `Dockerfile` em estágio único sobre `python:3.12-slim`:
- `ENV PYTHONUNBUFFERED=1 PYTHONDONTWRITEBYTECODE=1 PIP_NO_CACHE_DIR=1`
- `WORKDIR /app`
- Instalar apenas os pacotes de sistema realmente necessários (`ca-certificates`) e limpar `/var/lib/apt/lists`
- Criar usuário não-root `sysdoc` com UID/GID 10001 e diretório home `/home/sysdoc`
- Copiar o repositório para `/app` e rodar `pip install --no-cache-dir -e ".[web]"`
- Criar `/dados` com dono `sysdoc`
- `ENV SYSDOC_WEB_DATA_DIR=/dados HOME=/home/sysdoc`
- `USER sysdoc`
- `EXPOSE 8000`
- `ENTRYPOINT ["/app/docker/entrypoint.sh"]`

A imagem **não** pode conter `ENV` ou `ARG` com nome ou valor de chave de API. Não use `ARG` para segredo em hipótese alguma.

Criar `.dockerignore` excluindo, no mínimo: `.git`, `.planning`, `__pycache__`, `*.pyc`, `*.egg-info`, `dados_web`, `processo-teste`, `processo-01`, `output`, `documentos`, `Referencias`, `referencias`, `.sysdoc`, `node_modules`, `*.sqlite3`, `.env`. O material real do usuário (`processo-teste/`, `Referencias/`) nunca entra na imagem.

Criar `docker/entrypoint.sh` (`#!/bin/sh`, `set -eu`, bit de execução `chmod +x`) que executa nesta ordem:
1. Se `DJANGO_SECRET_KEY` estiver vazia, gerar uma e persistir em `${SYSDOC_WEB_DATA_DIR}/secret_key` com permissão `600`, reaproveitando o arquivo em subidas seguintes; exportar a variável. Assim `docker compose up` funciona sem o administrador inventar segredo, e o segredo não muda a cada reinício (D-02).
2. `python -m django --version` para falhar cedo e claramente se o extra `web` não estiver instalado.
3. `python manage.py migrate --noinput`
4. `python manage.py collectstatic --noinput`
5. `python manage.py sanear_jobs` (D-15)
6. Iniciar o worker em segundo plano num laço de reinício: um `while true; do python manage.py runworker --intervalo "${SYSDOC_WEB_INTERVALO_WORKER:-2}"; sleep 5; done &` — **exatamente um** processo worker, nunca dois (D-14).
7. `exec gunicorn sysdoc_web.wsgi:application --bind 0.0.0.0:8000 --workers 1 --threads 4 --timeout 120 --access-logfile - --error-logfile -`

O `--workers 1` é obrigatório e deve estar comentado no arquivo como a amarração a D-14. O `--threads 4` é mantido de propósito e também merece comentário: o paralelismo de thread serve ao polling de progresso e ao upload (plano 07-06), nunca à execução de análise, que continua no worker single-slot. Ele é seguro porque a corrida entre threads no SQLite já está tratada nas duas pontas — `DATABASES["default"]["OPTIONS"]["timeout"]` nas settings (plano 07-02) faz o driver esperar pelo lock em vez de falhar na hora, e `fila.enfileirar` converte tanto `IntegrityError` quanto `OperationalError` em `FilaOcupada` (plano 07-03). Sem essas duas defesas, `--threads 4` transformaria a recusa "análise em andamento" num 500 genérico. Nenhuma criação automática de superusuário: contas são criadas pelo administrador (D-07); o entrypoint apenas imprime, ao final da preparação, a linha `Para criar o primeiro usuário: docker compose exec web python manage.py createsuperuser`.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| host → container | Volume de dados e montagem de `~/.sysdoc` cruzam a fronteira |
| imagem → registro/repositório | Qualquer segredo embutido na imagem vaza com ela |
| rede → porta 8000 | Superfície HTTP exposta pelo compose |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-07-04-01 | Information Disclosure | imagem Docker | mitigate | Nenhum `ENV`/`ARG` de chave de API no `Dockerfile`; chaves chegam por montagem `:ro` de `~/.sysdoc` ou por env do administrador; teste `test_compose_nao_contem_segredo_literal` |
| T-07-04-02 | Information Disclosure | contexto de build | mitigate | `.dockerignore` exclui `processo-teste`, `Referencias`, `.sysdoc`, `.git`, `*.sqlite3` — material real do usuário nunca entra na imagem |
| T-07-04-03 | Elevation of Privilege | processo do container | mitigate | `USER sysdoc` (UID 10001), sem root em runtime; `/dados` com dono do usuário da aplicação |
| T-07-04-04 | Denial of Service | concorrência de análises | mitigate | `gunicorn --workers 1` e exatamente um laço de `runworker`; nenhum serviço adicional no compose (D-14). As 4 threads do gunicorn não driblam a trava: o slot único é imposto pela `UniqueConstraint` do banco, e a corrida de lock entre threads é absorvida pelo `timeout` do SQLite (07-02) e pelo tratamento de `OperationalError` em `fila.enfileirar` (07-03) |
| T-07-04-05 | Tampering | `DJANGO_SECRET_KEY` | mitigate | Gerada uma vez e persistida em `${SYSDOC_WEB_DATA_DIR}/secret_key` com permissão 600 dentro do volume; não regenerada a cada subida (sessões e tokens CSRF não são invalidados silenciosamente) |
| T-07-04-06 | Spoofing | `ALLOWED_HOSTS` | mitigate | Interpolado do ambiente com default restrito `localhost,127.0.0.1`; o compose nunca fixa `*` |
| T-07-04-SC | Tampering | camada base e `pip install` | mitigate | Base `python:3.12-slim` (imagem oficial); único `pip install` é `-e ".[web]"`, que resolve as dependências já auditadas em `pyproject.toml`; nenhum `curl \| sh` e nenhum pacote fora do índice padrão |
</threat_model>
